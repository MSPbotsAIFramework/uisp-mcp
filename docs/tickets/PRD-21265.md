## Product design

### Goals / Non-goals

**Goal**: a read-only MCP connector that lets an agent answer, for a given
UISP deployment: what sites and devices exist, what their current status
is, what network outages have happened recently (and which are ongoing),
and what shows up in the deployment's event/audit log — matching the four
nouns in the ticket (site, device, outage, event-log) and nothing more for
this first version.

**Non-goals** (out of scope for this ticket):
- No write/control actions of any kind — no device restart, no
  authorize/unauthorize, no firewall/DHCP/QoS/interface configuration, no
  maintenance mode, no backups. The ticket says "Review ... data"; the API
  has dozens of mutating endpoints (device config, firewall rules, DHCP,
  OSPF, ONU provisioning) that are deliberately not wrapped.
- No billing/CRM data (`ucrm`/`ucrmDetails` query params and the `Site.ucrm`
  object) — UISP's billing counterpart (UCRM) is a separate concern.
- No site/device search-by-free-text tool (`GET /sites/search`), no
  per-device interface/traffic/statistics breakdown
  (`/devices/{id}/interfaces`, `/devices/{id}/statistics`,
  `/sites/{id}/traffic*`), no data-links, gateways, background tasks,
  firmware catalog, or speed-test history. These are real, documented
  endpoints (and some are in `WYRE-AI/uisp-mcp`'s wider 27-tool surface)
  but are not what the ticket's four nouns ask for; listed under Known Gaps
  for a future ticket if a real need shows up (SOP §A4: tools are
  capabilities, not an API mirror, and capped at ≤20 per service — this
  design uses 6).
- No alert acknowledge/snooze workflow for outages — `GET /outages` is
  read-only in the spec itself; there is no mutating counterpart to wrap.
- No historical outage window beyond what the API itself retains (the
  spec's own summary says "last month" — see Tech design §7).

### Acceptance criteria AC1..ACn

- **AC1**: Given valid credentials for a UISP instance, When
  `uisp_list_sites` is called with no filter, Then it returns every site in
  that instance (id, name, type, status); given a `site_type` filter
  (`site` or `endpoint`), Then only sites of that type are returned.
- **AC2**: Given a known `site_id`, When `uisp_get_site` is called, Then it
  returns that site's detail (name, status, type, suspended flag); given an
  unknown `site_id`, Then it returns a `not_found` error, not a raw
  exception.
- **AC3**: Given a `site_id`, When `uisp_list_devices` is called, Then it
  returns the devices belonging to that site (name, model, role, type,
  status, authorized flag); given no `site_id`, Then it returns devices
  across all sites; given a `role` or `type` filter, Then only matching
  devices are returned.
- **AC4**: Given a known `device_id`, When `uisp_get_device` is called,
  Then it returns that device's identification and current overview
  (status, uptime, CPU/RAM load, outage score, last-seen time); given an
  unknown `device_id`, Then it returns a `not_found` error.
- **AC5**: Given no filter, When `uisp_list_outages` is called, Then it
  returns the outages the UISP instance currently retains (type
  `outage`/`unreachable`, start/end timestamps, ongoing flag, and the
  device and site each outage belongs to); given `in_progress=true`, Then
  only currently-ongoing outages are returned; given a `device_id` filter,
  Then only outages for that device are returned.
- **AC6**: Given optional `site_id` / `device_id` / `level` filters, When
  `uisp_list_logs` is called, Then it returns event/audit log entries
  (timestamp, severity level `info`/`warning`/`error`, message, tag, and
  the device/site the entry refers to) matching the filters; given no
  filter, Then it returns the instance's recent log entries.
- **AC7**: Given more outages or log entries exist than fit in one tool
  call's cap, When `uisp_list_outages` or `uisp_list_logs` is called, Then
  the tool paginates against the upstream API internally (the caller does
  not pass raw page numbers) and the response states whether it was
  truncated — no silent gap.
- **AC8**: Given the required gateway headers are missing on the request,
  When any tool is called, Then it returns the structured `not_configured`
  error envelope, not a raw exception or a 500.
- **AC9**: Given the UISP instance itself returns 401 (bad token), 404
  (unknown resource), or a 5xx/timeout, When any tool is called, Then the
  error is mapped to the matching structured code
  (`unauthorized`/`not_found`/`upstream_error`) — never a stack trace or an
  unhandled exception.
- **AC10**: Given a site/device/filter combination that matches nothing,
  When any list tool (`uisp_list_sites`, `uisp_list_devices`,
  `uisp_list_outages`, `uisp_list_logs`) is called, Then it returns an
  empty list with a normal success response, not an error and not `404`.
- **AC11** (isolation, required by the test-case quality bar): Given two
  different callers present two different `X-Uisp-Api-Key` /
  `X-Uisp-Base-Url` header pairs (two different UISP instances) and call
  any tool concurrently, Then neither caller's result or credentials leak
  into the other caller's response — exercised at the credential/header
  level, not just asserted from documentation.
- **AC12**: Given the server's `tools/list` response, When it is inspected,
  Then every tool is read-only (`readOnlyHint: true`) and there is no
  write/delete/restart/config tool present — the read-only scope in Goals
  is a verifiable property of the shipped server, not just a design
  intent.

## Tech design

### Conclusion

Build the first version of `uisp-mcp` from scratch (Python 3.12 + uv +
FastMCP, per SOP §A3/§9), mirroring the shape of this organization's other
read-only network-monitoring connector, `unifi-network-mcp`. Six read-only
tools, one HTTP client module, one credential-isolation middleware, no
upstream mutation, no new infrastructure: every tool is a thin, paginated
wrapper over one of `GET /sites`, `GET /sites/{id}`, `GET /devices`,
`GET /devices/{id}`, `GET /outages`, `GET /logs` on the target UISP
instance, reached directly (unlike UniFi, UISP has no cloud connector proxy
to go through — every deployment has its own reachable host, see §7).

### Option analysis

| Option | How | Pros | Cost | Verdict |
|---|---|---|---|---|
| A. Direct per-instance HTTP client, credentials = API token + target base URL | Server calls `{base_url}/nms/api/v2.1/...` directly with `x-auth-token`, both values supplied per-request via headers | Matches UISP's actual architecture (no shared cloud endpoint exists); zero new infrastructure; same request-per-tenant isolation model as every other connector in this org | Two required credential fields instead of one (vendor's own architecture requires it — UISP has no account-level identity the way `X-Unifi-Console-Id` resolves within one UI.com account) | **Chosen** |
| B. Treat it like UniFi's connector-proxy model (one shared upstream host) | Server would hard-code one base host and only take a token header | Simpler credential surface (one header) | Factually wrong for UISP — there is no Ubiquiti-operated shared proxy for UISP instances; every deployment is independently reachable at its own host. Would make the server unusable for the majority of customers (self-hosted UISP) | Rejected |
| C. Mirror all 27 endpoints `WYRE-AI/uisp-mcp` wraps | Wrap sites, devices, outages, logs, data-links, gateways, tasks, firmware, speed tests, discovered devices, etc. | Maximum capability parity with the reference implementation | Ticket asks for four specific nouns; SOP §A4 caps tools ≤20 and says tools are capabilities, not an API mirror; a wider surface is unreviewed, untested scope creep for a first version with no real test account | Rejected for v1 — see Non-goals / Known Gaps for how to grow it later |

### Data & API contract

**Credentials** (both required, read via request headers only — SOP §3.1,
no env-var fallback):

| Header | Type | Required | Description |
|---|---|---|---|
| `X-Uisp-Api-Key` | string (password) | Yes | UISP API token (`x-auth-token`), generated in the target UISP console at Settings → Users → your user → API tokens. A read-only token is sufficient and recommended for this server, since it issues no write calls. |
| `X-Uisp-Base-Url` | string | Yes | The full origin of the customer's UISP instance, e.g. `https://uisp.example.com` (no path suffix — the server appends `/nms/api/v2.1`). UISP has no shared multi-tenant cloud endpoint; every deployment, including Ubiquiti's own UISP Cloud-hosted tier, is reachable at its own host. |

Missing either header → `401` with the `not_configured` envelope, body
lists both header names (SOP §3.2).

**Tools**:

| Tool | Upstream call(s) | Parameters | Returns |
|---|---|---|---|
| `uisp_list_sites` | `GET /sites` | `site_type` (optional, `site`\|`endpoint`), `ip` (optional) | `{"sites": [{id, name, type, status, suspended}], "count": n}` |
| `uisp_get_site` | `GET /sites/{id}` | `site_id` (required) | `{id, name, type, status, suspended, updated}` |
| `uisp_list_devices` | `GET /devices` | `site_id` (optional), `role` (optional), `type` (optional), `authorized` (optional bool) | `{"devices": [{id, name, model, role, type, status, site_id, authorized}], "count": n}` |
| `uisp_get_device` | `GET /devices/{id}` | `device_id` (required) | `{id, name, model, role, type, status, site_id, overview: {uptime, cpu, ram, outageScore, lastSeen}}` |
| `uisp_list_outages` | `GET /outages` (looped over `page`, `count=100` per call) | `device_id` (optional), `in_progress` (optional bool), `max_items` (optional, default 200) | `{"outages": [{id, type, start, end, ongoing, device_id, site_id}], "scanned": n, "truncated": bool}` |
| `uisp_list_logs` | `GET /logs` (looped over `page`, `count=100` per call) | `site_id` (optional), `device_id` (optional), `level` (optional, `info`\|`warning`\|`error`), `max_items` (optional, default 200) | `{"logs": [{id, timestamp, level, message, tag, device_id, site_id}], "scanned": n, "truncated": bool}` |

**Errors**: `UispError.to_envelope()` maps UISP's own `Error` schema
(`{statusCode, error, message}`) to this server's fixed vocabulary:
`401`/`403` → `unauthorized`; `404` → `not_found`; `400` → `invalid_argument`;
`429` → `rate_limited`; `5xx`/timeout/connection failure → `upstream_error`.
`NO_TOKEN` (`not_configured`) when either header is missing. No tool ever
raises a raw exception to the MCP layer.

**Backward compatibility**: not applicable — this is the first version of
a brand-new server; there is no prior tool surface to stay compatible
with.

### Key flow / sequence

1. Gateway middleware reads `X-Uisp-Api-Key` / `X-Uisp-Base-Url` from the
   incoming request into a per-request `contextvars.ContextVar`; `finally`
   resets it after the request (SOP §3.3).
2. Agent calls one of the six tools.
3. Tool resolves a `UispClient(base_url, api_key)` via `client_factory()`;
   returns `NO_TOKEN` if either credential is absent (AC8).
4. For `uisp_list_outages`/`uisp_list_logs`: tool loops
   `client.get(path, params={"count": 100, "page": p, ...filters})`,
   accumulating items until the API reports the last page or `max_items`
   is reached (AC7). For the other four tools: a single `client.get(...)`
   call.
5. Tool projects the upstream object(s) down to the trimmed fields listed
   in §5 (token economy, SOP §A4) and returns `dump_json_capped({...})`.
6. Any `UispError` raised during the call is converted via
   `.to_envelope()` (AC2-AC6, AC9).

### Non-functional

- **Idempotency & concurrency**: every tool is `GET`-only; safe to call
  repeatedly or concurrently. No shared mutable state beyond a connection
  pool keyed per-request-credentials, not shared across requests — unlike
  `unifi-network-mcp` (one account, many consoles, so a shared connection
  pool is safe there), here every request can target a *different host*
  (`X-Uisp-Base-Url` varies by tenant), so the HTTP client itself must be
  constructed per-request, not pooled globally.
- **Performance**: `uisp_list_sites`/`uisp_list_devices` are single calls,
  bounded by `dump_json_capped`'s existing size cap. `uisp_list_outages`/
  `uisp_list_logs` are bounded by `max_items` (default 200 → at most 2
  upstream calls at `count=100`), so one tool call cannot fan out
  unboundedly against a large deployment's history.
- **Security**: no credential is cached, logged, or persisted beyond the
  request (SOP's three iron laws). TLS certificate verification stays ON
  by default (`httpx`'s default) — see Decisions made by DEV01 for why
  this is not relaxed for self-signed deployments. Response size is
  bounded by `dump_json_capped`'s existing cap.
- **Multi-tenant isolation**: the contextvar + per-request `UispClient`
  construction (keyed off that request's own `X-Uisp-Base-Url` +
  `X-Uisp-Api-Key`, never a global/module-level client) means two
  concurrent callers targeting two different UISP instances can never see
  each other's data — there is no shared state between them beyond the
  stateless HTTP transport (AC11).
- **Observability**: errors flow through the single `UispError`/

### Risks & dependencies

- **Risk**: the success path (a real API token actually returning
  site/device/outage/log data) is unverified — only the documented schema
  and a dummy-token 401/404 round-trip (planned for self-test, see
  Self-test note in the eventual dev-leg report) can be confirmed without
  a real UISP instance. Every existing connector in this org built without
  a test account (`unifi-network-mcp`) carries the same disclosed caveat;
  mitigate by keeping that same honest disclosure in this repo's Known

  will cause every call to fail with `upstream_error` until/unless a
  customer-specific override is designed — not fixed in this version (see
  Decisions made by DEV01); flagged so it is not mistaken for a bug when
  it is reported.

  gateway or control-plane change is needed (confirmed: this is a
  standard fixed-header-credential "plain vendor" shape for
  `/api/vendor-register`, not OAuth or special handling).

### Decisions made by DEV01

(2026-10-30 rule, `references/mcp-track.md` §2.4 — choices made without a
human to ask, repeated verbatim in a separate `[DESIGN DECISIONS]`
comment.)

- **Two required credential headers (`X-Uisp-Api-Key` + `X-Uisp-Base-Url`)
  instead of one** — because UISP has no shared cloud endpoint the way
  UniFi's `api.ui.com` connector proxy does; every deployment is its own
  host. Alternative considered: a single combined header (e.g.
  `token@host`) — rejected because it breaks the SOP §3.1 rule of one
  credential field per Header, and because the MCP Admin credential-entry
  form (label/type per field, set at `/api/vendor-register` time) is built
  around one field per Header, not a composite value the user has to
  construct themselves.
- **TLS certificate verification stays on (no `verify=False` option)** —
  rejected the tempting shortcut of disabling verification for self-hosted
  customers likely to run self-signed certs, because that would be a
  silent security regression (MITM exposure) applied to every tenant by
  default, not just the ones who need it. Self-signed instances will see
  `upstream_error` until a future, explicitly-opt-in mechanism is designed
  (see Risks) — failing loudly is the correct default, not failing open.
- **List endpoints return a trimmed field projection, not the raw upstream
  object** — `GET /sites` and `GET /devices` return the full nested
  `Site`/`DeviceStatusOverview` schema (QoS config, UCRM billing linkage,
  deprecated AirMax/AirFiber blocks, full interface lists, etc.), most of
  which answers questions this ticket does not ask. Projected down to the
  fields in §5's contract table (SOP §A4 token economy: return only the
  fields actually needed). `uisp_get_site`/`uisp_get_device` (single-resource tools) keep a
  slightly fuller projection since the caller already picked one specific
  target and is more likely to want detail.
- **`uisp_list_outages`/`uisp_list_logs` wrap the API's required
  `page`/`count` pagination in an internal loop capped by `max_items`,
  rather than exposing raw page numbers to the agent** — same technique
  `unifi-network-mcp/src/unifi_network_mcp/tools/alerts.py`'s
  `unifi_list_device_issues` uses for its own internal scan loop; an agent
  reasoning about "show me recent outages" should not have to manage
  pagination state across tool calls.
- **Scope frozen at the ticket's four nouns (sites, devices, outages,
  logs) — not the wider ~27-endpoint surface `WYRE-AI/uisp-mcp` covers** —
  SOP §A4 caps tool count and asks for capabilities matched to a real
  need, not an API mirror; the referenced third-party page is explicitly
  "inspiration," and the ticket's own wording ("Review site, device,
  outage, and event-log data") does not ask for billing, device
  configuration, or the long tail of per-protocol detail endpoints. Listed
  under Non-goals / Known Gaps for a follow-up ticket if real demand shows
  up.

## Self-test

Implemented per the Tech design above. One deliberate deviation from the
Data & API contract table, made during implementation (dev's freedom per
SOP, does not change any AC-visible behavior): `uisp_list_sites`'s
`site_type`/`ip` filters and `uisp_list_devices`'s `site_id`/`role`/`type`/

unfiltered list, not passed upstream as query parameters — the mirrored
OpenAPI document does not confirm server-side filter support for `GET

silently under- or over-return results with no error to catch it. Recorded
in README → Known Gaps. `uisp_list_outages`/`uisp_list_logs` still filter
after the internal pagination scan, exactly as designed.
