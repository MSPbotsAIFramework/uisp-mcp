### Findings

1. [must-fix] `src/uisp_mcp/api_client.py:102` (via `src/uisp_mcp/tools/_common.py:129` — `paginate_all`'s loop) — a brand-new `httpx.AsyncClient` is opened and closed inside `_request()` on every call to `UispClient.get()`. `uisp_list_outages`/`uisp_list_logs` call `paginate_all`, which calls `client.get()` once per upstream page (2 calls for the default `max_items=200` at `count=100`/page) — so a single tool invocation opens a fresh TCP+TLS connection per page instead of reusing one client/connection across the pages of that request. This is an explicit "must" in the SOP this review is scored against: `~/.claude/skills/vendor-mcp-development/reference/vendor-mcp-development-sop.md:274` ("连接复用：在一次请求内复用同一个 HTTP client（连接池），不要每调一个端点就新建一个 client"), repeated as a non-optional §14 checklist line (same file, "一次请求内复用同一个 HTTP client"). It also contradicts this ticket's own Tech design, which describes "a connection pool keyed per-request-credentials" (`docs/tickets/PRD-21265.md` → Non-functional → Idempotency & concurrency) — no pooling is implemented at all, not even within one request. Fix: thread a single `httpx.AsyncClient` through the pagination loop (construct it once per tool call / per `UispClient.get`-sequence, close it after the loop finishes), not once per upstream page.
2. [must-fix] `src/uisp_mcp/api_client.py:31-34,97-125` — the retry/backoff budget can push a single tool call's upstream latency past the SOP's hard 120s cap. `_TIMEOUT` allows up to ~35s per attempt (`connect=5.0` + `read=30.0`) and `_MAX_RETRIES=3` means up to 4 attempts, plus `2**attempt` backoff sleeps of 1s/2s/4s between them: worst case ≈ 4×35s + 7s ≈ 147s, over the SOP's explicit "单次工具调用总耗时（含重试）必须 < 120s" (`vendor-mcp-development-sop.md:273`, repeated in the §14 checklist). This isn't a theoretical corner case — it is exactly the scenario the retry logic exists for (a struggling/degraded UISP instance returning 5xx or timing out), and in that scenario the MCP call itself would now run long enough to look hung to whatever is calling it. Fix: track elapsed time across attempts and stop retrying once the budget would be exceeded, or tighten the read timeout / retry count so the worst case provably stays under 120s.

### Fixes

Fixed in `fa22757` on `dev/PRD-21265` (base unchanged, `main @ 818862a`, no new upstream commits to sync).

1. **Must-fix #1 (connection reuse)** — `src/uisp_mcp/api_client.py`: `UispClient` now creates its `httpx.AsyncClient` lazily on first use and caches it on `self._client`, reusing it for every subsequent `get()` call made through that same instance instead of opening/closing a fresh client inside `_request()` per call (`api_client.py:93-146`, was `api_client.py:97-125` in `c17dee0`). Added `UispClient.aclose()` to release the connection once the caller is done. All six tool functions (`sites.py`, `devices.py`, `outages.py`, `logs.py`) now call `await client.aclose()` in a `finally` block around their existing `try/except UispError`, so the client-per-request contract (fresh per MCP request, reused within it) is upheld end to end — `paginate_all`'s multi-page loop (`tools/_common.py:110-143`, unchanged) now shares one connection across all of its `client.get()` calls instead of opening one per page.
   - Regression coverage: `TC-UISP-121` (`test_every_tool_closes_its_client`) asserts every tool closes its client; `TC-UISP-122` (`test_real_client_reuses_one_http_connection_across_calls`) monkeypatches `httpx.AsyncClient.__init__` to count instantiations and asserts exactly one is created across a 2-page `paginate_all` call against the real `UispClient` (not the stub).
   - Live verification beyond the test suite: `scratch/PRD-21265/smoke.py` drives the real ASGI app in-process (no mocks) through `initialize` → `tools/list` → `tools/call uisp_list_sites` and `tools/call uisp_list_logs` (the paginating tool) against an unreachable host; both calls returned a single structured `upstream_error` envelope with no unhandled exception or connection leak, confirming the `aclose()` path is exception-safe even on the retry/error branch.

2. **Must-fix #2 (120s cap)** — `src/uisp_mcp/api_client.py:31-41`: tightened `_TIMEOUT.read` (30.0s → 20.0s) and `_MAX_RETRIES` (3 → 2), i.e. 3 total attempts instead of 4. New worst case, including every retry running the full `connect+read` timeout and every backoff hitting the `Retry-After`-driven `_MAX_BACKOFF_SECONDS` cap (not just the exponential default): `3 attempts * (5.0 connect + 20.0 read) + 2 retries * 5.0 max backoff = 85.0s`, under the SOP's 120s hard cap with a 35s margin — versus the previous ≈147s worst case the review flagged. Chose tightening the static constants (this review's second suggested option) over runtime elapsed-time tracking: the result is provable by reading the constants rather than by reasoning about a clock-based early-exit path, which is simpler to verify in review and keeps the retry logic itself unchanged.
   - Regression coverage: `TC-UISP-123` (`test_retry_backoff_worst_case_stays_under_sop_120s_cap`) computes the same worst-case formula from the live `_TIMEOUT`/`_MAX_RETRIES`/`_MAX_BACKOFF_SECONDS` constants and asserts it stays under 120.0s, so a future constant change that reopens this gap fails CI rather than needing a human to redo the arithmetic.
